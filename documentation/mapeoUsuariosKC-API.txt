*********************************************************
******************* RAZONAMIENTO ************************
*********************************************************
Ambas DB tienen la restricción unique tanto en el email como en el username, sirven como identificador.
El claim (atributo) "sub" nos recupera el identificador de la DB del user_entity. Es lo más serio usar este identificador.
Si se elige el email, no permitiremos que el usuario modofique su correo electrónico en el futuro pues es el identificador.
Si se elige el username, pasará lo mismo, no tendremos donde agarrarnos para mapear. 
	--> Entonces, la DB de la API debería tener su user_id mapeado con el id de la DB de Keycloak que recuperamos en cada petición a través del claim "sub". 
	--> Los campos adicionales que guarde la tabla de user de la API serán redundantes o complelemtarios con los de la DB de keycloak.
	--> La responsabilidad recae en la DB de keycloak y la API solo tiene su user_id para su lógica interna, el auth_server_id y los campos email y username, proveídos en el access Token.
	--> El campo pass_word se reemplaza por auth_server_id que será el identificador del usuario en keyloak y nuestro mapeo entre las dos DB.
	--> La cantidad de caracteres de la DB de la API no puede ser menor a los de KC, ya que si se crea uno largo en KC y la API lo rebota, queda creado en KC.

----------------\
------------------\
-------------------> RESULTADO: vamos a mapear las dos DB a través del campo keycloak.user_entity.id = app.users.auth_server_id. Modificar: llevar a 255 el varchar de email y username en ciuco.
------------------/  Ventaja de este aproach: nos permite independizarnos del servidor de autorización, sólo necesitamos un punto de anclaje para mapear.
----------------/
